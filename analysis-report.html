Service Worker 是专为 Vortex 部署场景（build:vortex）设计的。普通 npm run build 和 npm run develop 不包含 SW —— 通过条件编译实现。

二、为什么引入 Service Worker？

核心诉求：离线可用 + 秒开体验。Vortex 是私有化部署场景，网络环境可能不稳定，SW 确保应用在弱网或断网时仍能正常打开。

2.1 三个核心考量

考量说明
离线可用 首次加载后核心资源写入 Cache Storage，断网时直接从缓存加载，应用照常运行
秒开体验 Cache-First 策略，后续访问零网络请求，比 HTTP 缓存更可控更激进
PWA 能力 配合 manifest.json 实现全屏安装、.ply 文件关联（双击 PLY 文件直接用 SuperSplat 打开）

2.2 设计决策

为什么手写而不是用 Workbox？
  • 预缓存的资源列表是固定的、数量少（仅 19 个 URL），不需要 Workbox 的复杂路由和策略组合
  • 零额外依赖，代码仅 ~60 行，完全可控
  • 构建集成简单：Rollup 单独入口独立打包即可，无需额外插件
为什么不用 skipWaiting + clientsClaim？
这个项目刻意采用了保守策略——新版本 SW 不会立即接管页面，等用户关闭所有旧 Tab 后才激活。这避免了运行时缓存被突然替换导致的资源版本不一致问题。代价是用户需要刷新页面才能用上新版本。

2.3 条件编译机制

// rollup.config.mjs — 构建时替换
const BUILD_SW = process.env.BUILD_SW === 'true';  // 读取环境变量

replace({
    'process.env.BUILD_SW': JSON.stringify(BUILD_SW),  // → "true" or "false"
})

// src/main.ts — 运行时注册
if (process.env.BUILD_SW) {        // 构建后变成 if ("false") { ... }
    navigator.serviceWorker.register('./sw.js')
}

非 PWA 模式下，if (false) 被 terser 完全移除。同时 SW 入口仅当 BUILD_SW=true 时才加入 Rollup 构建配置，所以 dist/sw.js 根本不会生成。

四、版本化缓存实现

核心在 src/sw.ts，全链路如下：

package.json: "version": "2.27.4" │ ▼ Rollup json() 插件内联 src/sw.ts → import { version } from '../package.json' │ appVersion = "2.27.4"（硬编码进 SW 产物） ▼ cacheName = `superSplat-v${appVersion}` │ = "superSplat-v2.27.4" ▼ ┌─ install ─────────────────────────────────────┐ │ caches.open("superSplat-v2.27.4") │ │ .then(cache => cache.addAll(cacheUrls)) │ └────────────────────────────────────────────────┘ │ ▼ ┌─ activate ────────────────────────────────────┐ │ caches.keys().then(names => │ │ names.filter(n => n ≠ "superSplat-v2.27.4") │ │ .forEach(caches.delete) │ │ ) │ └────────────────────────────────────────────────┘

每次构建新版本部署后，SW 文件内容变化 → 浏览器触发新 install → 新 activate 时删除所有非当前版本的缓存桶，用户本地始终只保留一份缓存。

五、三个生命周期事件

事件触发时机SuperSplat 中的行为
install 首次注册 SW
或 SW 文件任何一个字节变化时		 event.waitUntil(caches.open(cacheName).then(cache => cache.addAll(cacheUrls)))
— 一次性预缓存全部核心资源
— 任一 URL 下载失败（如 404）→ 整个 install 失败 → 旧 SW 继续工作
— 未调用 self.skipWaiting()
activate install 成功 + 所有旧 SW 页面关闭后 遍历 caches.keys()，删除非当前版本缓存桶
— 未调用 clientsClaim()，旧页仍由旧 SW 控制直到刷新
fetch SW 控制范围内的页面每次发起 HTTP 请求 event.respondWith(caches.match(request) ?? fetch(request))
— Cache-First：命中 → 返回缓存；未命中 → 走网络
— 不写回缓存（非 cacheUrls 资源每次都走网络）

版本更新流程

用户首次访问 │ ▼ install → 预缓存所有核心资源 │ ▼ activate → 清理旧版本缓存 │ ▼ fetch → 之后每个请求先查缓存，未命中走网络 ══════════════ 某天发布新版本 ══════════════ 新 SW install 成功（浏览器检测到 sw.js 变化） │ ▼ 等待所有旧 Tab 关闭（用户不感知，旧页面照常工作） │ ▼ 旧 Tab 全部关闭 → activate → 删旧缓存桶 → 建新缓存桶 │ ▼ 用户下次打开 → 使用新版本

六、SW 可以访问什么？

SW 运行在 ServiceWorkerGlobalScope 中，完全独立于页面。代码中的类型声明：

declare let self: ServiceWorkerGlobalScope;
类别✓ 可用✗ 不可用
存储 caches、IndexedDB、CacheStorage localStorage、sessionStorage
（同步阻塞 API，SW 中直接禁用）
网络 fetch、WebSocket XHR 同步版
生命周期 install、activate、fetch、message 事件 —
页面通信 self.clients（Clients API）
BroadcastChannel、MessageChannel		 window.postMessage（没有 window）
推送 / 通知 Push API、Notification API —
后台任务 Background Sync —
DOM — document、window
所有 DOM API 完全不可用
隐含前提：代码中直接写 caches.open()、caches.keys()、caches.match() 之所以能工作，是因为 caches 是 ServiceWorkerGlobalScope 的原生属性——就像页面里可以直接写 window.localStorage 一样，不需要 import。

七、多页面共享同一个 SW

┌──────────────┐ ┌──────────────┐ ┌──────────────┐ │ Tab A │ │ Tab B │ │ Tab C │ │ index.html │ │ viewer │ │ editor │ └───────┬──────┘ └───────┬──────┘ └───────┬──────┘ │ │ │ │ 每个 Tab 通过 navigator.serviceWorker │ 拿到独立的 ServiceWorkerContainer 引用 │ 但都指向同一个 SW 注册实例 │ │ │ └──────────────────┼──────────────────┘ │ ▼ ┌─────────────────────┐ │ Service Worker │ │ (sw.js) · 唯一实例 │ │ │ │ cacheName = │ │ superSplat-v2.27.4 │ └─────────────────────┘

四个关键结论：

  1. SW 是跨页面的：同源下所有受控页面共享同一个 SW 实例。缓存（Cache Storage）自然也是共享的。
  2. SW 生命周期独立于页面：所有 Tab 关闭后 SW 仍可存活一段时间（浏览器空闲回收策略决定），下次打开页面时无需重新 install。
  3. 更新只发生一次：当 SW 文件变化时，浏览器只做一次字节对比和 install，不会每个 Tab 各触发一次。
  4. self.clients 可以遍历所有受控页面：SW 知道自己管了多少个 Tab，可以通过 Clients API 与它们通信。

八、Scope 与请求拦截全流程

8.1 Scope 控制范围

navigator.serviceWorker.register('./sw.js');  // scope 默认 = sw.js 所在目录 = ./
请求是否拦截原因
/index.html受控scope 内
/static/icons/logo.png受控scope 内
/static/locales/en.json受控scope 内
/subpage/index.html受控scope 内（根路径覆盖所有子目录）
https://api.example.com/data不受控跨域，不在 scope 下
https://cdn.example.com/splat.sog不受控跨域

这也是为什么 cacheUrls 全是 ./ 开头的路径——只有这些在 scope 内，fetch 事件才能拦截到它们。

8.2 单次请求拦截流程

Tab 请求 ./index.js │ ▼ 浏览器：scope 匹配？ ──是──▶ SW 的 fetch 事件触发 │ ▼ caches.match(request) │ ┌─命中──┐ ┌─未命中─┐ │ │ │ │ ▼ │ ▼ │ 返回缓存 │ fetch(request) │ (零网络) │ │ │ │ ┌─成功─┘ └失败─┐ │ │ │ │ ▼ ▼ │ 返回网络响应 错误页面 │ (不写回缓存) │ │ └──────────────────┘ │ ▼ response 返回给页面
注意：第 58 行 response ?? fetch(event.request) —— 网络请求的结果不会被自动写回缓存。非 cacheUrls 里的资源每次都走网络，SW 仅充当透明代理。如果想运行时缓存新资源，需要自行调用 cache.put(request, response.clone())。

9.3 Shared Worker：特殊的中间态

跨页面共享同一个 Worker 实例（类似 SW），但不能拦截网络请求（没有 fetch 事件）。常用来共享 WebSocket 连接或跨 Tab 状态同步。

// page-a.html
new SharedWorker('shared.js').port.postMessage('hello from A');

// page-b.html — 拿到的是同一个 worker 实例！
new SharedWorker('shared.js').port.onmessage = e => console.log(e.data);
// → "hello from A"
回到你的代码：declare let self: ServiceWorkerGlobalScope 这行告诉 TypeScript 当前文件的 self 是 SW 的全局作用域。如果写的是 Dedicated Worker，应该声明为 DedicatedWorkerGlobalScope。两者的 self 上 API 交集很大（都有 caches、fetch、postMessage），但 SW 独有的能力（skipWaiting、clientsClaim、event.waitUntil）在 Dedicated Worker 上不存在。
